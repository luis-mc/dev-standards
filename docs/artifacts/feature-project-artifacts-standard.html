§ 1What and why

A project builds many things at once. Its owner needs to see, at any moment, what is live, what is running and what needs them, without reading code or chat.

What the owner asked for (9 and 10 October):

  • Same look and feel for every artifact within a project, with sections always numbered and section 0 always Status and checklist.
  • Feature artifacts (“Feature: <name>”) describe something to build in one app, several apps or the whole project. They evolve, and log every change in a History table as their last section.
  • One full-progress artifact per project (“Full Progress: <project>”): the owner’s view of all ongoing work in the project, across every app and service. It holds every feature task and every other project task; it is not only a summary of the feature artifacts.
  • Creating a feature artifact when the project has no full-progress artifact creates the full-progress artifact too.
  • Status changes update the artifacts automatically: a feature task’s change updates its feature artifact, and any project task’s change updates the full-progress artifact.
  • Built in dev-standards as the plugin luismc-artifacts, with explicit names in the code: feature artifact and full-progress artifact, never a generic “page”.

Why it matters. In an earlier project the pages drifted: a feature page still said “Needs you” for a step finished hours before. The status was typed by hand in two places. This design writes each status once and generates every view of it.

§ 2The design

Each task’s status is stored once, in a task registry inside the full-progress artifact. One command changes it, regenerates every checklist that shows the task, and a hook makes sure both artifacts are published before the turn ends.

Two kinds of project artifact

KindTitleHoldsHow many
Feature artifactFeature: <name>One feature: why, design, rules, tests, decisions, its tasks, History last.Any number
Full-progress artifactFull Progress: <project>All ongoing work in the project: every feature task (linked to its feature artifact) and every project task. Embeds the task registry.Exactly one

What makes it automatic

LayerWhat it does
Rule file.claude/rules/project-artifacts.md, installed in a project when its first project artifact is created. Sessions record every piece of work as a task and run task-status-update at each status event.
After-command hookWatches for known events (gh pr create, gh pr merge, deploys, failed checks) on a branch named with a task ID, and queues the status change.
End-of-turn hookIf a status change is queued or a changed artifact is unpublished, the turn cannot end; it lists what is missing. This is the guarantee.
Session-start hookCatches changes made between sessions (CI finished, a PR merged on GitHub) and queues them.

The plugin cannot publish an artifact by itself; only the session’s Artifact tool can. The hooks make sure the session does it. All hooks do nothing in a project without the manifest.

Where things live

  • The repo is the record. Each project keeps docs/artifacts/: manifest.json (each artifact’s link), registry.json (the task registry), each artifact’s content and its last published HTML. A deleted artifact is recreated from it.
  • No duplicates. An artifact is created only when its manifest link no longer opens and no artifact with the same title exists; the new link is written back to the manifest.
  • Status changes commit to the default branch as docs-only commits. CI ignores docs/**, and hosting skips docs-only deploys.
  • Task IDs are a registered prefix plus a number (AR5, DS4), unique across the project. Branch names start with one: AR5-artifactspec.

§ 3The rules

The draft of ARTIFACTSPEC 1.0.0. Each rule has an ID so the spec, the checks and reviews can cite it.

Kinds and tasks

IDRule
AS1A project has feature artifacts and exactly one full-progress artifact. Creating the first feature artifact creates the full-progress artifact if none exists.
AS2A feature artifact is titled Feature: plus the feature name. It covers one app, several, or the whole project, and changes as the feature evolves. Its last section is History: Date | Change, newest first.
AS3The full-progress artifact is titled Full Progress: plus the project name. It shows all ongoing work in the project, across every app and service: every feature task, linked to its feature artifact, and every project task. It has no History; Live or Done rows older than 14 days fold into an “Earlier” block.
AS4Every task has an ID: a prefix registered in the manifest plus a number. IDs are unique across the project and never reused.
AS5Each task’s state is stored once, in the task registry docs/artifacts/registry.json, committed in the project’s repo and embedded in the full-progress artifact. Every checklist and tile count is generated from it; no status row is typed by hand.
AS6The manifest docs/artifacts/manifest.json names the project, its timezone, its design, the full-progress artifact, and each feature artifact with its link, task prefix and files.

Look and structure

IDRule
AS7Every artifact of a project uses the shared structure stylesheet unchanged, plus the project’s design tokens: taken from the project’s own design (design-token files, theme configuration, CSS custom properties or its live site), or the plugin’s default design when it has none. Artifact-only drawings may add styles but never change shared ones.
AS8Sections are numbered from 0 in order with no gaps; the contents list shows the same numbers. Section 0 is Status and checklist: stamp, lede, tiles, key and checklist, in that order.
AS9The stamp reads Last update: DD Mon HH:MM (<timezone label>), with the full ISO time in its datetime attribute, taken from the real clock at the moment of the change.
AS10The lede says in plain words what stands and what needs the owner, or “Nothing needs you”.
AS11The checklist columns are Status | Item | Detail | Expected. Rows are grouped: Running now and next (Running, Waiting, To do), Needs you, failed or on hold (Needs you, Failed, On hold), Live or done, newest first. The full-progress artifact adds an App / service column after Item. Expected is a date, with a time for work due within a day (10 Oct ~14:15), in the owner’s time zone. The zone is set once in the manifest and named in the column header. Never “today” or “soon”. When an expected time passes, a new estimate replaces it.
AS12Eight statuses with fixed colours and meanings: Live released or in production; Done finished, nothing to release; Running being worked on now; Needs you waits on the owner; Waiting waits on something else (CI, a dependency, a time); To do planned, not started; On hold paused by decision; Failed broke and needs a fix or a decision.
AS13Artifacts work in light and dark themes, and at phone width with a 16 px side gutter and no sideways page scroll; wide tables scroll inside their box.

Keeping them current

IDRule
AS14A feature task’s status change updates its feature artifact and the full-progress artifact; any other project task’s change updates the full-progress artifact. One command does both, and every changed artifact is published in the same turn.
AS15Every piece of work a session starts in the project is recorded as a task first: on its feature artifact, or as a project task.
AS16Branch names start with the task ID, so hooks can match events to tasks.
AS17A turn may not end while a status change is queued or a changed artifact is unpublished.
AS18Times are shown in the owner’s timezone and labelled with it.
AS19A project’s artifacts can be recreated from docs/artifacts/ alone. A new artifact is created only when the manifest link no longer opens and no artifact with the same title exists.
AS20Status changes are committed to the default branch as docs-only commits; CI and hosting skip docs-only changes.

The five skills

SkillWhat it does
/luismc-artifacts:feature-artifact-newAsks the feature name and the apps it covers, writes a feature artifact with section 0 started and a first History row, registers it in the manifest, and adds its tasks to the registry. Creates the full-progress artifact first if the project has none.
/luismc-artifacts:full-progress-artifact-newWrites the project’s one full-progress artifact with an empty task registry; refuses if one exists. For a project with ongoing work but no feature artifact yet.
/luismc-artifacts:task-addRecords new work as a task, asking which artifact owns it (a feature artifact, or the project), and gives it the next ID.
/luismc-artifacts:task-status-updateReads the artifacts, runs set-task-status, runs the check, and publishes every artifact that changed. Retries after a publish conflict.
/luismc-artifacts:project-artifact-checkChecks a project’s artifacts against ARTIFACTSPEC. Exit 0 clean, 1 findings, 2 unreadable, like spec_check.py.

The default design is in design/default-design.css and templates/project-artifact.css on branch AR14-default-design; these two artifacts use it.

§ 5Requirements and tests

IDRequirementTest that proves it
R1Titles start with “Feature: ” or “Full Progress: ” (AS2, AS3).A feature artifact titled “Manga” fails; “Feature: Manga” passes.
R2Exactly one full-progress artifact, created with the first feature artifact (AS1).Project with none: feature-artifact-new creates both. Project with one: no second is created. Manifest with two: fails.
R3Section 0 first and named “Status and checklist” (AS8).Section 0 named “Status” fails.
R4Sections numbered from 0, in order, no gaps (AS8).A gap, a repeat and an unnumbered section each fail with their line.
R5Stamp format, ISO attribute and timezone label (AS9, AS18).“Last update: 9/10 7am” fails; a stamp without datetime or label fails.
R6Checklist columns: Status | Item | Detail | Expected on a feature artifact; Status | Item | App / service | Detail | Expected on the full-progress artifact (AS11).A fifth column, or reordered columns, fails. An Expected value on an open row that is not a date (today, soon) fails.
R7Only the eight statuses (AS12).“Merged” as a status fails and names the nearest allowed word.
R8Every row sits in its status’s group (AS11).A Live row under “Running now and next” fails.
R9Checklists and tiles equal the registry (AS5).A hand-edited row, or a tile saying 3 Live over 2, fails.
R10Every feature task is on the full-progress artifact, linked to its feature artifact (AS3).A feature task missing from the full-progress artifact fails.
R11Task IDs unique and their prefixes registered (AS4).Two tasks named AR5, or an unregistered prefix, fail.
R12History is the last section of a feature artifact, Date | Change (AS2).No History, or History not last, fails.
R13Structure stylesheet unchanged; theme tokens free (AS7).A changed structure rule fails; a changed theme colour passes.
R14One command updates every artifact that shows the task (AS14).set-task-status AR5 running: both artifacts show Running with new stamps.
R15Hooks queue and block (AS16, AS17).gh pr merge on branch AR5-x queues AR5; the end-of-turn hook blocks with a queue and passes without one; no manifest, no effect.
R16Phone width and both themes (AS13).A fixture artifact at 360 px wide has no sideways scroll in light and dark (manual check listed in the skill).
R17Recreate without duplicates (AS19).Manifest link deleted: one new artifact, manifest updated. Link alive: nothing created. Same title exists: no new artifact, manifest repaired.

§ 6Decisions

#QuestionDecision (10 Oct)
1How is a task’s status stored so both artifacts update automatically?One task registry inside the full-progress artifact; both checklists are generated from it.
2Do branch names start with the task ID?Yes (AR5-artifactspec), so hooks can match events to tasks.
3How do changes made outside a session reach the artifacts?At the next session start, through the session-start hook. No cloud routine in 1.0.
4What look do artifacts get?The project’s own design, found by scanning its design files, theme configuration, CSS custom properties or live site. A project with no design gets the plugin’s default design. dev-standards uses the default.
5An App / service column on the full-progress artifact?Yes, on the full-progress artifact only.
6Where is the record kept?In the repo, docs/artifacts/, committed to the default branch as docs-only commits; a deleted artifact is recreated from it without duplicates. Replaces the first answer that the published artifact is the record.
7How does a project get the plugin?luismc-project-setup installs it in every project it sets up; it can also be installed on its own in any project. No artifact is created until the first feature artifact.
8Which clock do Expected times use?The owner’s time zone, per project, set in the manifest and named in the column header.
9Does dev-standards move other projects onto the plugin?No. dev-standards ships the plugin and names or changes no other project; each project adopts it in its own sessions.

§ 7What the review changed

The review of the first proposal on 10 October found twelve problems. Each one changed the design above.

FindingChange
A status was typed by hand in two places, the cause of the drift.One task registry; one command regenerates every checklist (AS5, AS14).
The discipline was a sentence in CLAUDE.md, the form that already failed.Hooks queue status changes and block the turn until artifacts are published (AS17).
No source of truth and no list of a project’s pages.The repo record in docs/artifacts/ is the source; the manifest lists every artifact, and a deleted one is recreated from it (AS5, AS6, AS19).
Per-project look contradicted the byte-identical stylesheet check.Structure stylesheet fixed, theme tokens free (AS7, R13).
A project name and “Lisbon” hard-coded; old and duplicate CSS rules.Project name and timezone come from the manifest; the stylesheet is rebuilt clean (AR6).
Spec and code disagreed on the groups and the History columns.One definition each (AS2, AS11).
HTML parsed with regular expressions; it left broken CSS on this artifact.The script uses Python’s built-in HTML parser.
Python’s zoneinfo has no timezone data on Windows without the tzdata package.Fallback to the machine’s local time, with a warning.
The stamp had no year and nothing a program could compare.ISO time in the datetime attribute (AS9).
The rule would have gone into every project’s CLAUDE.md.A rule file installed only where project artifacts are used.
The progress page would grow forever.Live or Done rows older than 14 days fold into “Earlier” (AS3).
Generic names: “page”, luismc-pages, .st.Feature artifact and full-progress artifact throughout; plugin luismc-artifacts; readable class names in AR6.
