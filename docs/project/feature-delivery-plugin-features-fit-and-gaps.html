§ 1What the plugin is

luismc-delivery keeps a release train moving without the owner watching it. A ledger (.delivery/ledger.json) records trains, agents, questions and publishes. Hooks read it and block a turn that leaves work half done. A background watcher pushes the next train, opens its pull request, waits for CI on the head commit and merges at green. Shared scripts (gate, join, CI watch, cleanup) are written into a product by the installer.

Rules live in DELIVERYSPEC (DL-nn). The feature spec is docs/features/delivery/spec.md. A project with no .delivery/ folder gets no delivery hooks. Exception: the machine load guard, which is on wherever the plugin is enabled.

Scope after DS245: the runner pool is gone. DS246 (To do) removes the load and slot layer too, because CRSP will own machine limits. What stays: tasks, RELEASE-n, train flow, when CI starts, how finished CI is detected, and merge.

§ 3How it fits with the other plugins

Plugin or pieceLink to delivery

CRSP (own project, later)Will own machine limits, slots and runners. Delivery keeps one question: is CI done, on which head.

A project turns delivery on with a .delivery/ folder and a config.json. The docs and setup plugins work without it. Delivery needs the record from the docs plugin.

§ 5Gaps to fill

Ranked by how many stops or hours the evidence shows.

  1. Watcher does post-merge smoke and cleanup itself. About 280 stops in project A come from smoke and cleanup left to the agent. The watcher already merges. It should run cleanup.py and the smoke when the project has a smoke command, and stop the agent only on failure. Benefit: fewer stops, no uncleaned merges. Quality kept: same checks, same ledger writers.
  2. Stale watcher detection and restart. 4 of 6 heartbeats are days old. SessionStart should restart a dead watcher, not only say so.
  3. Default ETA by task type. 102 no-ETA stops in A, 64 and 76 events in C and E. A table of defaults (docs change, small fix, feature) removes the stop. The agent states a figure only when it differs.
  4. One-command onboarding. Two projects have nothing. delivery-ci-setup exists; a "turn on delivery here" step with safe defaults (warn mode) would close this.
  5. "Waiting past Expected" rows. Warn once and move the row to "Needs you", instead of stopping each turn.
  6. Runner-offline back-off. Repair loops of 8 to 18 cycles show no back-off. After DS246 this belongs to CRSP. Delivery should only report "CI cannot start" and wait.
  7. Warn-to-block path. Three of six projects sit in warn mode with no path to block. A report "would have blocked N times" lets the owner choose.

§ 6What to remove or simplify

  • Ledger jobs and held_runs: 0 entries in all six projects (seen). Remove them, with the matching brief text (R5.59).
  • Empty config keys long_pole_globs, measure_globs, update_state_files, heavy_commands: empty everywhere (seen). Remove from the schema. checks_off stays as the escape hatch.
  • Load, slot and runner layer (DL-77 to 79, 90, 91): already planned as DS246. The evidence supports it: 78 load blocks in A are noise that CRSP will handle at the runner.
  • "Say RELEASE-n" stop (DL-64): 59 blocks in A and over 1,900 transcript hits. Fix the wording automatically, or make it a warning (guess: low value).
  • Per-agent "not checked for N min" stop (DL-32): 127 blocks. The watcher can check agents and write last_checked itself (guess).
  • Silent "no gate": gate is "none" in D and used in one project only. Keep the gate. Make "no gate" an explicit choice the doctor shows.
  • PostToolUse "boom" crashes: find the cause or confirm test noise, then remove it.
  • Runner-variable requirements (R5.63, R5.64 and similar): they describe the runner layer. Move them to the change log once DS246 lands.
